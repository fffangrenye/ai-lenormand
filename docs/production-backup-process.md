# Flora 生产业务备份与补货

业务主数据在 `flora-v3-api` 的 SQLite Durable Object。Supabase 仍提供身份认证；以下流程备份业务数据和账号 ID 映射，不是 Supabase Auth 密码、身份及会话的完整备份，也不替代其独立恢复方案。

## 数据位置与保密

- 正式历史、花瓣批次与余额、充值码摘要/状态/核销、签到与业务流水：Cloudflare 生产对象。
- 可发货的完整充值码：管理员导出的私有 TXT 以及运营者导入的闲管家卡密仓库。数据库不保存完整码明文；导出依赖原签名密钥。
- 生产备份：本机私有 `.local-paid/production-backups/<backup-id>/`，逐文件 gzip 后使用 AES-256-GCM 加密。
- 解密密钥：分开放在 `.local-paid/production-backup-keys/<backup-id>.key`。原充值码签名密钥也加密保存在备份中，用于灾后恢复原库存。
- 这两个目录限制为当前 Windows 用户及 SYSTEM 访问；所有生产文件和密钥均被 Git 忽略。GitHub 只保存工具、测试、流程和脱敏回执。
- 本机备份独立于 Cloudflare，但尚不是异地副本。运营者应将加密备份另存到自己选定的私有网盘或离线介质，解密密钥另行安全保存。未指定目标前不上传用户数据。

## 一致性与访问方式

维护入口只存在于后端的私有服务绑定，不由正式网页转发。每个维护请求要求原签名密钥的 HMAC、管理员身份白名单、独立用途和最长五分钟有效期；接口没有任意 SQL 执行功能。

`node scripts/connect-private-maintenance.cjs` 通过官方、令牌保护的临时 edge preview 建立仅监听 `127.0.0.1:3114` 的本机通道，不创建公开维护路由。结束后停止进程，令牌不写入文件。使用现有 Wrangler 登录及网络代理；不要把此 helper 部署成公开 Worker。

备份开始时用同步事务记录 schema、各表行数及 rowid 上限，安装临时写时复制保护。导出期间变化的行只保存第一次变动前的内容，页查询将旧内容与未变动行合并；新插入和 rowid 重用不会混入早先的快照。每页最多 128 行，目标约 750 KB；不整体读入内存，不重建索引或重写旧历史。

完成导出立即结束快照并清除本次临时保护。快照最多 45 分钟，过期后保护不再增加临时数据，页面读取拒绝继续，不能将未完成文件标成有效备份。异常退出须核对旧快照 ID 后执行 `backup-end` 清理，再开始新的备份，不能混合两个时间点的数据。

## 私有配置与执行

`private-maintenance-client.cjs` 的 JSON 配置只放在忽略目录，字段为 `endpoint`（本机通道）、`secretsFile`、`signingKeyFile`、`stockDirectory`，可指定 `actor`。不要将真实私有配置提交仓库。

新补货请求文件必须在调用前持久保存套餐、数量、生成和导出的请求标识及原因；同一次任务重试复用同一请求文件，避免创建第二批库存。本次工具要求明确的 `single`、200 个，使用正式前缀 `FLORA-`。

```text
node scripts/generate-production-stock.cjs <私有配置文件> <本次补货请求文件>
node scripts/production-backup.cjs <私有配置文件> <本次备份请求文件>
node scripts/verify-production-backup.cjs <加密备份目录> <解密密钥文件> <本次新库存TXT>
```

备份请求文件包含唯一 `id`、备份 `directory`、`keyFile`。备份工具支持从已完成的加密分片继续，最多三个独立表并行下载，每个表仍严格按游标顺序读取；不会将失败或过期导出标成成功。不要同时执行两次备份。

## 恢复验证与生产恢复边界

验证工具校验每份文件的摘要、GCM 认证、清单与分片归属/顺序，恢复完整 SQLite schema、rowid、数据和索引，执行完整性与外键检查，并逐表重新计算全部内容摘要。它还用原业务代码读取历史，在本机副本演练一花瓣兑换、同账号重试和跨账号拒绝；演练事务撤回，并复核原金融数据摘要。

验证完成后删除演练产生的本机明文数据库，保留加密备份与脱敏验证报告。验证还逐个核对本次补货 TXT 的全部码与恢复库存中的摘要、权益及价格。不会对正式站执行恢复、真实兑换、充值或退款。程序接口可显式指定 `restoreTo` 来保留独立恢复副本，但仅应由授权维护操作使用，且不得覆盖现有文件。

文件的离线可恢复性与生产快照清理分别记录。已完整导出的文件可先做隔离恢复验证，但交付时还须确认 `index.json` 的 `snapshotEnded: true` 及生产 `inspect.activeBackup: null`。重试结束快照不会重新导出历史或抹掉已验证状态。Cloudflare 发布后 Worker 与 Durable Object 的代码版本可能短暂不同，不应因此重新迁移业务数据或重复生成库存。

真正恢复正式站时，须先保全当时的现状、确认目标时间点，核对该时间点之后的购买/兑换/花瓣变化，再在新的隔离对象中恢复并验证，最后切换。禁止直接用旧备份覆盖仍在接单的生产对象。Supabase Auth 仍需单独保全；同一用户 ID 是关联历史和权益的依据。

## 闲管家补货

新批次的 TXT 一行一码，且已与此前本机交付文件去重。只导入对应的“1 花瓣”卡种一次，每件商品发 1 个码；不导入旧批次、不将已发出但未兑换的码当成未售库存，也不自动回库重售退款码。

生成、导出不等于已经导入闲管家。交付回执保留明确的“等待用户导入”状态，实际导入由运营者完成并记下时间。
