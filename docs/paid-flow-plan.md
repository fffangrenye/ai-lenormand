## 当前实现与改造原因

- `lib/reading-quota.ts`：当前每日 3 次。该每日计数不能直接充当永久余额，否则无法追溯购买、签到、退款和消费来源。
- `app/api/deep-reading/route.ts`：已做生成前预占、失败退回；仍需增加稳定请求标识、服务端记录归属核验和结果持久化。
- `lib/project-store.ts`：当前主解读生成后由客户端写回完成结果。付费版必须把结果保存和消费确认移到服务端，避免断网后丢结果或重复扣次。
- `app/api/deep-reading/follow-up/route.ts`：当前根据请求中的 `messages` 统计成功追问；不能作为收费后的权限依据。应查询服务端记录，原子预留追问槽位，保存成功后计次。
- 当前客户端提交问题、牌面和上下文。解锁及追问时应改为提交记录 ID 和请求标识，服务端核验所属账号并读取已保存牌面，不能信任客户端提供的权益或历史。
- `app/daily/page.tsx`：当前每次在浏览器随机抽牌，尚不是账号每天唯一的持久化签到。
- 现有迁移允许用户管理自己的解读、牌面和追问记录。付费新增的解锁状态、消费关联和助手回答应仅允许可信服务端写入；所有权限制本身不足以防止用户伪造权益。
- 现有零额度结果页提供复制 Prompt，付费版需检查页面、历史、导出及接口，避免继续提供未解锁内容。
- 当前主解读提示词约 300–500 中文字、1400 输出 token、45 秒超时；追问 420 输出 token。主解读升级需单独评估长度、耗时与质量，追问保持原有深度。

## 权益与记录设计

以账号为单位管理权益，客户端只读自己的余额和流水，不能直接增减次数。

| 数据 | 用途与约束 |
| --- | --- |
| 权益批次 | 记录首次赠送、老用户赠送、签到、购买和补偿；关联来源、可用量、预留量、消耗量及退款冻结量 |
| 次数账本 | 每次变动记录业务事件唯一键、批次、解读或订单、原因和时间；业务重试不重复入账 |
| 解读任务 | 关联原问题、固定牌面、请求标识、预留批次、状态、执行租约和已保存结果 |
| 追问任务 | 每条已解锁解读最多两个成功槽位；并发预留也占槽，失败可释放 |
| 签到记录 | 账号和北京时间日期唯一；先保存牌，再产生文案，同日两个入口返回同一记录 |
| 奖励里程碑 | 账号和第几个累计三天周期唯一，与签到及账本一致提交 |
| 订单与支付事件 | 服务端锁定价格快照；渠道交易号唯一；订单已支付与权益已到账分别可查 |
| 管理审计 | 核款、补偿、调整与退款均记录操作者、原因及关联业务 |

一次主解读只需要一个额度批次；优先赠送，赠送内部按获得时间消耗，再使用购买批次。退款冻结和回收只针对对应订单的购买批次。

当前本地交互流程（按后续反馈调整）：问题与牌阵 → 用户手动选满牌位 → 保存固定牌面 → 自动预留 1 花瓣并解读 → 服务端保存结果并确认消费。开始前明确告知费用；余额不足或失败时原牌仍保留，用户可在原记录重试。旧已锁定记录仍可主动解锁。

模型调用不能与数据库长事务绑在一起。生成前后使用短事务，配合请求去重、执行租约和版本校验。恢复任务先核对结果是否已经保存；过期任务只有在未完成且持有正确租约时才能释放预留。旧任务迟到的结果不得再次扣次或覆盖新任务。

支付流程：用户选套餐与方式 → 服务端创建锁价订单 → 接收并验证支付事件 → 同一事件原子入账一次 → 返回原记录 → 用户主动使用 1 次解锁。支付成功跳转和“我已付款”都不能直接增加余额。

历史解读迁移：保留原已完成记录的可访问性，不补扣额度。首次赠送按启用版本和账号去重，新老用户分类需确定明确的启用时间。历史记录剩余追问如何从旧的一次规则过渡到两次，应在迁移测试中明确，不默认为全部重新赠送两次。

## 分版实施与验收

| 版本 | 实施范围 | 必须通过的验收 |
| --- | --- | --- |
| V1：权益和解读 | 集中商品配置、权益批次及账本、赠送去重、服务端解锁与保存、2 次追问、零余额保留原牌、主解读质量升级 | 不重复赠送；并发不透支；断网可找回同一结果；失败恢复；第三次追问拒绝；余额为零仍能追问旧记录；未解锁内容不泄露 |
| V2：每日签到 | 双入口同牌、月历、累计签到、每 3 天奖励 | 同日只签一次；第 3/6/9 天各奖励一次；断签跨月不清零；午夜日期正确；文案失败不丢签到 |
| V3：模拟购买 | 套餐页、方式选择、订单、模拟支付通知、到账返回原牌、管理核款、补偿及退款 | 成功/失败/取消/延迟/重复通知正确；改价不改旧单；重复到账被阻止；退款不影响其他批次；关闭页面后仍可查询 |

V1 的第一项交付是隔离环境与数据约束，再做权益接口和页面。订单、签到需要的通用批次与账本在 V1 预留，后续扩展不重写扣次逻辑。

每版交付本地入口、中文测试步骤、可用功能及未完成项，再根据试用反馈调整。真实支付接入另行安排。

## 本地开发和测试边界

- 后续实现使用独立本地分支，先保全现有未提交的额度与 Yes / No 改动，不做清理或重置。
- 优先使用本地 Supabase 验证事务、权限和迁移。无可用隔离数据库时，采用可持久化的本地测试适配器；明确说明尚未验证真实数据库权限和事务实现，不能把内存模拟测试当成上线验收。
- 独立本地环境配置，启动时校验数据库、认证、模型与支付目标；生产地址或真实支付配置一律阻止本地付费测试写入。
- 默认使用模拟模型，不产生真实模型调用费用；使用可控时钟验证跨天、跨月和累计奖励。
- 普通用户、管理员、越权账号分开测试；模拟支付和测试账号入口在生产模式强制关闭。
- 不连接生产数据库执行迁移、发放权益或调整余额；不推送、不部署、不发生真实支付。
- 数据库变更后续以迁移文件交付；本轮没有创建或执行数据库迁移。

## 上线前另行解决的事项

- 免费政策已确认；后续明确历史追问权益和管理员权益如何迁移，并验证旧每日额度停用后不再重复发放。
- 支付宝正式接口或个人码人工核款的选择；PayPal 实际结算币种及对应价格。当前套餐表只是 CNY 产品方案，不代表已核实渠道支持。
- 真实账号、回调地址、退款流程和售后文案；密钥通过环境配置，不进入聊天或前端。
- 检查用户此前提供书籍是否在授权范围内可访问；未检索与验证前不宣称已经融合书籍知识。
- 对固定问题及同类牌阵比较升级前后结果：有效信息、组合证据、重复率、截断、耗时及模型用量。缺乏实测时不承诺成本或时延。
- 记录赠送、签到奖励、实际消耗、购买转化和退款。文档奖励力度意味着持续签到约每月赠送 10 次主解读；保留该方案，后续根据真实数据由用户决定是否调整。
