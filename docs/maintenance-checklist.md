# Flora 维护与发布检查

## 每次发布

使用 `npm ci` 安装 package-lock.json 固定的依赖；发布工具要求 Node.js 至少 22，推荐 Node.js 24 LTS。不要混用旧 pnpm 锁文件。

1. 在隔离工作目录修改，生产数据库检查默认只读；禁止拿用户真实充值码或花瓣做测试。
2. 检查类型、运行依赖公告、源码和产物密钥扫描。执行业务测试时把依赖不同环境变量的测试文件放在独立进程，避免模块缓存影响测试结果。
3. 运行主解读、两次追问、重复兑换、并发扣次、跨账号访问、签到奖励、批量抽牌恢复回归。
4. Cloudflare 原生本地运行时验证完整生产包，覆盖静态页、登录、账户、充值、兑换和动态项目地址；同时检查公开维护接口关闭。
5. 提交并推送源码后通过 `release-production.cjs` 发布。脚本记录完整提交号、分支、各项检查状态、耗时以及发布前的 Worker 版本；无法取得回滚版本则停止发布。
6. 正式站检查公开页面与静态标记、资源可加载、匿名接口权限、旧链接跳转和客服链接。需要用户亲自完成真实账号的成功登录与手机 Safari/Chrome 体验。
7. 将不含用户数据和密钥的版本回执提交到 docs/releases。仅改前端时，后端与跳转 Worker 继续记录各自实际部署的旧提交。

回滚先选回执中的旧 Worker 版本。核实静态资源版本、服务绑定和数据库兼容性；不要回滚数据库或覆盖原账本。未经本地完整验证的依赖升级不发布。

## 周期检查

- 每周及重大版本后：手机登录/退出/切换账号，历史分页、抽牌断线恢复，签到同日重复、第三天奖励，兑换后余额与流水。
- 每周：Supabase 数据库实际大小、各表和索引占用、认证健康、RLS 与特权函数权限；Cloudflare 请求、SQL 读写、AI 用量。关闭前端埋点不代表 Supabase 触发器也已关闭。
- 每周：旧历史来源与冻结迁移清单的记录数、最大创建时间；发现增量先核对，不自动重新迁移、不覆盖新站内容。
- 每次批量发码/重大数据变更后及至少每周：独立加密业务备份、校验文件哈希，并定期在隔离环境验证恢复。Auth 备份与 Cloudflare 业务备份分开管理；GitHub 不是用户数据备份。
- 每月及续费前：检查域名注册商的到期时间、自动续费状态、付款方式和通知邮箱。RDAP 查到到期时间也不能证明已启用自动续费。
- 每月：核对所有公开客服 mailto 链接。网页链接存在不代表邮箱能正常收信，需运营者实际收发测试。

## 数据与权限检查边界

只读统计报告不等于逐条内容核对。备份行数相同也不能单独证明正文一致；必须记录核验的快照时间、哈希、恢复回执和无法验证的范围。解密含用户正文的备份需在明确授权范围内进行。

管理员仅依据后端验证后的身份与服务端白名单授权，不信任请求头、客户端余额或 user_metadata。定期检查 Supabase 自动确认邮箱与验证码策略；`email_confirmed_at` 有值不一定代表用户确实点击过验证邮件。
